# Сетевая игра RTS: клиент, мини-сервер игрока, сервер диспетчера

> Перевод [`docs/reverse/multiplayer.md`](../../reverse/multiplayer.md).
> Основной текст — английский: при расхождении верен он.

Разобрано только для чтения на копиях, 2026-11-03:
- `rts1.exe` (`build/ida/rts1.i64`);
- `rts_server.exe`, консольная сборка пользователя
  (`build/srv/rts_server.i64`);
- `rts_server_DSP.exe` (`build/dsp/dsp.i64`, см. `dispatcher.md`).

Сетевые журналы сервера пользователя использовались только для подсчётов.
В них настоящие адреса и ники игроков, и сюда они не копируются.

## Три программы, три роли

| Программа | Роль |
|---|---|
| `rts1.exe` | Три роли: <ul><li>клиент игрока;</li><li>**мини-сервер игрока** («Player-mini-server»), запускаемый из внутриигрового меню в одиночной игре;</li><li>**узел-собеседник** для связи с помощником (помощником машиниста).</li></ul> |
| `rts_server.exe` | Выделенный сервер со встроенным пультом диспетчера (`TfPult`, «RTS Dispatcher»), порт по умолчанию 800. Он включает собственный код симуляции RTS (физика поездов, модуль маршрутов, сигналы, экспорты DLL вроде `_SpeedLimit`). Он решает за: <ul><li>стрелки, сигналы и время;</li><li>виды поездов и назначения;</li><li>поезда ИИ и статические (PROBABLE).</li></ul> |
| `rts_server_DSP.exe` | Тот же исходник, собранный как клиент диспетчера для `rts_server.exe` (`dispatcher.md`). |

## Транспорт и обрамление — CONFIRMED

**Транспорт.** Обычный TCP через WinSock 2, управляемый `WSAAsyncSelect`
на скрытых окнах:
- «RTS Simulator Listener»;
- «RTS Server Listener»;
- «Player listener window»;
- «RTS DSP Listener»;
- «RTS Network Node \<name\>».

UDP нет.

**Пакет:**
- `u16 id`;
- `u32 length` (весь пакет, включая 6-байтовый заголовок);
- полезная нагрузка.

Нагрузки вкладывают пакеты с тем же обрамлением, например:
- `0x4603` содержит `0x4604` на каждый вагон;
- `0x4620` → `0x4621` → `0x4628` → `0x4629` / `0x462A`.

Данные — little endian. Строка — `u16` символов, затем UTF-16 с
завершающим нулём.

**Пределы:**
- сервер читает вход не больше 64 байт;
- после входа пакет пользователя не больше `0x3C00` (15 360) байт;
- иначе сервер отключает пользователя (`0x47FF`);
- клиент принимает от сервера до `0x1388000` байт (стартовый снимок);
- NetworkNode принимает не больше `0x1000` байт от связи, которая себя не
  назвала.

У ответа на вход и ответов-ошибок нет поля длины (ниже).

## Вход — CONFIRMED

Клиент → сервер (`rts1.exe` `0x4C1818`, `rts_server.exe` сторона
диспетчера `0x44D904`):

| Поле | Значение |
|---|---|
| `u16` | `0x4600` игрок (`rts1.exe`), `0x4500` диспетчер (`rts_server_DSP.exe`) |
| `u32` | `12 + 2n` |
| `u16` | версия протокола, 101 |
| `u16` | `n`, длина ника, 1..15 |
| UTF-16 | ник с завершающим нулём |

Адрес — «host:port»:
- `rts1.exe` разрешает его в IPv4 или IPv6;
- диспетчер разрешает только IPv4, порт 800, если не указан.

Сервер → клиент при успехе (`rts_server.exe` `0x4436C8`, мини-сервер
`0x4D0D8C`; читает `0x4C1B64`), без поля длины:

| Поле | Значение |
|---|---|
| `u16` | `0x4600` |
| `u16` | 101 |
| строка | описание: название маршрута, «Сценарий: …», «Сезон: …» |
| `u8`, `u8` | сезон, погода |
| строка | id маршрута |
| `4 × u32` | числа маршрута: стрелки, сигналы и ещё два. PROBABLE: электросекции и подстанции (`rts1.exe`: «Route count of electrosections doesn't match server's») |

Клиент проверяет маршрут и числа (`0x47A1A0`). При несовпадении он
показывает «у вас нет нужной версии маршрута».

При ошибке сервер отправляет только код `u16` и закрывает соединение:

| Код | Смысл |
|---|---|
| `0x4701` | ник занят |
| `0x4702` | <ul><li>сервер не принимает новых игроков или новых диспетчеров: отдельный переключатель для каждого вида;</li><li>на мини-сервере: имени нет в его списке игроков.</li></ul> |
| `0x4703` | стартовые данные уже отправлены (второй `0x4608`) |
| `0x4704` | первый пакет ни `0x4500`, ни `0x4600` («Probably wrong engine version») |
| `0x4705` | версия протокола не 101 |
| `0x4706` | поток пакетов (ограничения пакетов сервера), затем отключение |
| `0x47FD` / `0x47FE` / `0x47FF` | отключение: ошибка приёма / тело обрезано / плохая длина или отклонённый пакет |

**Переподключение.** На выделенном сервере вход с ником, который он уже
держит, — не «занят»: новый сокет прикрепляется к этому пользователю
(«User N reconnected»). Главный поток проверяет имя в течение 12 с
(`0x442A94`, и список запретов тоже). Мини-сервер отвечает `0x4701`, пока
это имя подключено.

**Стартовые данные.** После ответа клиент отправляет `0x4608`. Сервер
отправляет снимок своего мира:
- `0x4600` (корень);
- `0x460D` время;
- `0x4609`, затем `0x460A` на каждую стрелку;
- `0x460B`, затем `0x460C` на каждый сигнал;
- электрификация `0x4646`..`0x4648`;
- пункты погрузки и глобальные объекты `0x464B`..`0x464E`;
- поезда: `0x4607`, `0x4603` (`0x4606`) и груз `0x461C` на каждый;
- игроки `0x462D`;
- `0x4608`, чтобы его завершить.

Мини-сервер отправляет то же (`0x4D14F0`). `rts1.exe` пишет это в
`multdata` и загружает из него игру (`0x4CAEAC`).

Затем в меню клиент ждёт («Waiting for assignment…»):
- `0x4601` назначает ему поезд («Received assignment!!! Train number»);
- `0x461F` типа 1 делает его помощником;
- `0x461E` означает «Waiting for synchronization with engineer».

## Клиент в игре (`rts1.exe` с `rts_server.exe`) — CONFIRMED

**Соединение.**
- Сокет входа из меню остаётся открытым в игре: окно «RTS Simulator
  Listener», журнал `logmult.txt`.
- `0x460A`, `0x460C`, `0x460D` и `0x4616` применяются в сетевом потоке по
  мере прихода; остальное ставится в очередь главного цикла.
- **Когда сокет закрывается** (`FD_CLOSE`), клиент ставит в очередь свой
  собственный `0x4612` (`0x4CB390`). Его обработчик:
  - показывает «Server down, simulator will now quit»;
  - пишет файл восстановления сетевой игры (`0x47B09C`);
  - выходит.

  Переподключения в игре нет: любое оборванное соединение заканчивает
  игру. Следующий вход может восстановить положение («Restore player
  position»). Замечено 2026-11-03 при перезапуске пробного посредника.

**Собственный поезд игрока (вид PLAYER):**
- симулируется на месте: физика, DLL, кабина;
- пока он движется, `0x4603` идёт на сервер не чаще раза в 1,5 с
  (`0x5DC` мс, `0x424488`) и ещё раз, когда он останавливается;
- нагрузка:
  - id поезда, скорость (+92), ускорение (+96), положение, +272, +292;
  - на каждый вагон `0x4604`: положение `f64` и два float.

**Любой другой поезд:**
- берётся из `0x4603`, которые пересылает сервер;
- между обновлениями его положение экстраполируется с этими скоростью и
  ускорением;
- через 5 с без обновления скорость и ускорение падают до 0.

Клиент никогда не берёт положение сервера для своего поезда, кроме
`0x462F` (принудительное положение).

События клиент → сервер:

| Id | Что |
|---|---|
| `0x460A` | стрелка: номер, ветка, блокировка (сервер обрабатывает сразу, `0x40C52C`) |
| `0x460E` / `0x460F` | расцепить / сцепить |
| `0x461B` | действие меню вагона: выделенный сервер пересылает его остальным, каждый клиент его выполняет (хост мини-сервера выполняет сам) |
| `0x4639`, `0x463A`, `0x463D` | PROBABLE: изменился орган кабины локомотива игрока. Отправляются из обработчиков переключателей кабины (`0x437AA4`, `0x437E64`, `0x438430`, `0x438708`), ограничиваются сервером по частоте, пересылаются, чтобы другие видели огни, токоприёмники и звуки |
| `0x462D` | положение игрока, значок человека для Ctrl+F7 (пересылается с добавленными id и именем пользователя) |
| `0x4636` | состояние вагонов с блоками `0x4638` — UNKNOWN в подробностях |
| `0x4649` | CONFIRMED (2026-11-04, клиент `0x4CF464`): нагрузка подстанции — подстанция, фаза (int16), энергия, просуммированная за окно, его длина в с (`0x5B6030` отправляет его каждые 2 с, пока линия нагружена); пересылается только диспетчерам |
| `0x4640`, `0x4641`, `0x461D` | UNKNOWN |

Сервер → клиент:

| Id | Что |
|---|---|
| `0x460C` | показание сигнала (номер, показание, …) |
| `0x460A` | ветка и блокировка стрелки |
| `0x460D` | время суток |
| `0x4605` | вид поезда, подвид, номер (номера вагонов, биты 18+), начальное состояние — PROBABLE |
| `0x4613` | тормозные давления поезда, который не принадлежит игроку (четыре значения на вагон). PROBABLE: то, что задаёт форма диспетчера «Тормоза» |
| `0x4610` | id поезда изменился (после сцепки; см. «Сцепка в игре») |
| `0x4611` | текстовое сообщение диспетчера («Dispatcher») |
| `0x4616` | сервер приостановлен (пауза) |
| `0x4601` | назначение поезда |

## Выделенный сервер (`rts_server.exe`) — CONFIRMED, если не отмечено

**Потоки и соединения:**
- поток слушателя (`0x444658`: bind и listen; `0x442E8C`: accept);
- по потоку на соединение («Started thread %i for connection from address
  %s»);
- очередь и поток отправки на пользователя («PlayerOut semaphore %i»);
- адрес, который продолжает ошибаться, блокируется; есть `banlist.txt`.

**Вход.** Первый пакет задаёт вид: `0x4500` — диспетчер (вид 1), `0x4600`
— игрок (вид 0).

**Права:**
- `0x4508`, `0x4509`, `0x4602`, `0x4605`..`0x4607`, `0x4613` и `0x461A` от
  игроков отбрасываются;
- диспетчеру кроме вида нужен бит разрешения;
- `0x4645`..`0x4647`, `0x464A` и `0x464B` (электрификация, пункты
  погрузки) принимаются только от диспетчеров;
- `0x4648` отбрасывается от любого.

**Ограничения частоты.** Два счётчика на пользователя: все пакеты, и
`0x4639` / `0x463A` / `0x463D`. Они проверяются по ограничениям пакетов в
настройках сервера. При превышении сервер отвечает `0x4706` и отключает.

**Маршрутизация** (`0x4436C8`, отправляет `0x442E8C`). Пакет идёт в
главный поток (мир сервера), или пересылается, или и то, и другое.
Пересылаемый пакет отправляется одной из пяти аудиторий:

| Аудитория | Кто получает |
|---|---|
| 1 | один пользователь |
| 2 | все в игре, кроме отправителя |
| 3 | пользователи одного вида (диспетчеры) |
| 4 | все, кроме отправителя, чьё положение игрока (`0x462D`) в пределах 3 000 м от поезда, который называет пакет (`0x442E10`). Пакет, не называющий известного поезда, не отправляется |
| по умолчанию | все в игре |

Какие id куда идут:

| Id | Пересылаются | Сервер читает |
|---|---|---|
| `0x461B`, `0x461D`, `0x463F` | аудитории 2 | нет |
| `0x4617`, `0x4639`, `0x463A`, `0x463C`, `0x463D` | аудитории 4 | нет |
| `0x461C`, `0x4636`, `0x4640`, `0x4641` | аудитории 2 | да |
| `0x4649` | аудитории 3 (диспетчеры) | да |
| другие id | не пересылаются | только главный поток |

Особые случаи:
- `0x4649` идёт только диспетчерам;
- `0x4608` запрашивает снимок.

Главный цикл — `TfPult::MainTimerTimer`, «main dispatcher function».

**Диспетчеры** тоже получают пакеты мира, и свои `0x4504`..`0x450E`.
PROBABLE: списки игроков и поездов, `0x450A` — поезда для схемы.

**Сетевой журнал.** Пишется с настройкой «lognetpackages» / трассировки
данных и скрывает частые пакеты, если не поднять уровень трассировки
(`0x46BB98`):
- уровень 1 и выше: `0x4603`, `0x4606`, `0x4607`, `0x4617`, `0x4620`,
  `0x4623`, `0x4624`, `0x4630`, `0x463C`;
- уровень 2 и выше: `0x4609`, `0x460B`, `0x460D`, `0x4618`, `0x4619`,
  `0x4622`, `0x462D`, `0x462E`, `0x4632`, `0x4639`, `0x463A`, `0x463D`,
  `0x463F`.

Поэтому журналы пользователя не показывают положений поездов. Один
8-часовой сеанс примерно на 50 пользователей:
- клиенты отправили по несколько сотен `0x460A` и мало что ещё;
- сервер отправил 220 000 `0x460C`, 83 000 `0x460A`, 15 000 `0x4613` и
  8 000 `0x4605`.

## Сцепка в игре, в том числе поездов двух игроков — CONFIRMED, если не отмечено (2026-11-04)

Прочитано по `rts_server.exe` и `rts1.exe`. Ниже А и Б — два игрока: поезд А
наезжает на поезд Б.

**Виды поездов.**
- На сервере (`+296`): 0 STATIC, 1 PLAYER, 2 TRAFFIC, 3 LOOSE. Нумерация
  PROBABLE: она следует списку пульта и тому, как сервер их использует
  (ниже).
- На клиенте поезд PLAYER другого игрока становится видом 2 с флагом
  `0x10000` (обработчик `0x4607` в `0x4C3DE0`). Его положение приходит в
  `0x4603`.

**1. Сцепку замечает клиент поезда, который наезжает** (его физика вызывает
`0x469ED8`):
- его собственный поезд (вид 1) всегда забирает другой: если другой — его
  собственный, они меняются местами;
- сначала клиент ждёт, прокачивая сеть, пока у любого из поездов стоит флаг
  `0x800`: не больше 500 × 50 мс (`0x4CDF30`). `0x4610` снимает этот флаг.
  PROBABLE: `0x800` отмечает поезд, который ждёт id от сервера;
- он сцепляет у себя и шлёт `0x460F`: id своего поезда, id другого и по
  одному байту на конец каждого поезда.

**2. Сервер** (`0x40FB90`, случай `0xD` → `0x4501E0`):
- вагоны другого поезда встают к поезду отправителя с этого конца, где надо —
  развёрнутыми, с пересчитанными положениями; каждый вагон теперь
  принадлежит поезду отправителя; другой поезд удаляется (`0x457F44`) и
  уходит из списков пульта;
- **два игрока:** если оба поезда PLAYER у разных владельцев и Б в сети,
  сервер снимает Б с поезда: `0x4601` с байтом 0 для Б (`0x44ECAC`);
- `0x460F` (id общего поезда, старый id Б, оба байта концов) — всем, кроме
  отправителя (адресат 2);
- только для двух игроков: `0x4610` (старый id Б, id общего поезда) — Б
  (адресат 1);
- `0x4603` / `0x4604` общего поезда — всем, кроме отправителя (`0x44F2F0`).

**3. Все остальные клиенты** повторяют сцепку по `0x460F` (`0x469ED8` с
выставленным `0x631E76`: без обмена местами).

**4. Игрок Б:**
- поезд Б входит в поезд А, который на клиенте Б — поезд другого игрока
  (вид 2): его положение теперь приходит из `0x4603` от А;
- поезд игрока на клиенте (`0x61D680`, PROBABLE) переезжает на общий поезд,
  и тот получает флаг `0x20`. Б остаётся в своей кабине; поезд двигает
  симуляция А. PROBABLE: управление Б туда ничто не передаёт (семейство
  `0x4639` только показывает другим огни, пантографы и звуки);
- в игре у клиента нет обработчика `0x4601` (его читает только меню ожидания
  назначения, `0x461F00`), так что клиент Б не узнаёт, что его сняли;
- `0x4610` называет старый поезд Б, которого уже нет: клиент пишет в журнал
  «не найден» (событие 5), и ничего не меняется.

**Чего RTS не делает:**
- скорость для поездов двух игроков не считается: вагоны соединяются как
  есть;
- Б не становится помощником: помощников назначает только диспетчер;
- расцепка потом — `0x460E`, и id отцепленной части выбирает сервер (клиент
  читает его в `0x631E78` перед разделением, `0x469858`). Кому достаётся
  отцепленная часть, не прослежено.

**Сцепка, которую делает сам сервер** (`0x40DCDC`; поезда LOOSE сервер
двигает сам, статический состав, который толкнули без сцепки, становится
LOOSE):
- движущийся поезд, дошедший до STATIC или LOOSE, забирает его со скоростью
  `(v1·m1 + v2·m2) / (m1 + m2)` (PROBABLE: `0x458E80` — масса);
- дойдя до поезда PLAYER или TRAFFIC, он сам входит в этот поезд, и
  `0x460F` уходит всем. `version.txt`: «состав типа PLAYER или TRAFFIC
  поглощает LOOSE»;
- PROBABLE: поезд LOOSE, простоявший 30 с, становится STATIC.

**Оба клиента сразу (PROBABLE).** Когда оба поезда едут навстречу, сцепку
могут заметить оба клиента:
- каждый сцепляет со своим поездом во главе и шлёт `0x460F`;
- сервер выполняет первый пакет. Второй называет поезд, которого уже нет, и
  `0x458EC0` ничего не находит;
- на Б серверный `0x460F` называет поезд А, который Б уже забрал, и тоже
  отбрасывается (событие 5). Затем `0x4610` переименовывает общий поезд Б в
  id А: похоже, `0x4610` нужен именно для этого;
- на Б этот общий поезд остаётся видом 1: оба клиента будут его считать и
  слать его `0x4603`. Отбрасывает ли сервер положения от игрока, который
  поездом уже не владеет, не прослежено.

## Мини-сервер игрока (`rts1.exe`) — CONFIRMED

**Запуск:**
- Внутриигровое меню (Ctrl+Alt+F7) предлагает «Configure server», только
  пока нет подключения к серверу, то есть в одиночной игре (`0x462FC8`).
- В диалоге (`0x534710`, `0x4C3990`) есть:
  - запуск;
  - имя сервера;
  - «только эти игроки» со списком имён.

**Узел.** Это NetworkNode с именем «Player-mini-server» (тип 2, флаги
`0x1054`). Он слушает первый свободный порт из `useportsfrom`..`useportsto`
в `config.ini` (по умолчанию 801..16000).

**Его обработчик** (`0x4CA588`) знает один вход, `0x4600`:
- версия 101, имя 1..15 символов;
- имя, подключённое сейчас или совпадающее с именем самого сервера:
  `0x4701`;
- со списком — имя не из него: `0x4702`;
- неверная версия: `0x4705`;
- имя из 0 или больше 15 символов: соединение обрывается.

`0x4608` получает снимок живого мира хоста.

**Хост действует как сервер:**
- запросы стрелок `0x4642`, когда стрелка не заблокирована и не
  забронирована;
- сцепка и расцепка `0x460E` / `0x460F`;
- действия меню вагона `0x461B`, выполняемые на хосте;
- положения игроков `0x462D`, пересылаются;
- физика поезда и пакеты кабины `0x4620`..`0x4624` и `0x4632`
  (`0x4C9120`).

Поток отправки (`0x5CEA84`) отправляет мир хоста:
- сигналы `0x460C`;
- стрелки `0x460A`;
- время `0x460D`;
- поезда `0x4603` / `0x4620`;
- состояние кабины `0x4624`….

«Assign to player…» трек-контроля отправляет `0x4601`.

**Без диспетчера.** Ветки `0x4500` нет, и нигде в `rts1.exe` нет пакета
`0x45xx`: константы `0x45xx` там — id кусков сохранения.

## Помощники (помощник машиниста) — CONFIRMED (поток), PROBABLE (подробности)

`disablehelpers` в `config.ini` их выключает.

1. Диспетчер назначает помощника. Сервер отправляет машинисту `0x461F`
   типа 2:
   - добавить или убрать;
   - id и имя помощника;
   - сеанс.
2. Клиент машиниста запускает свой NetworkNode (тип 1, флаги `0x1034`).
   Узел:
   - ждёт этого собеседника;
   - открывает порт для прослушивания в 801..16000;
   - отвечает `0x461F` (`0x4CD878`).
3. Сервер отправляет помощнику `0x461F` типа 1:
   - имя машиниста;
   - адрес IPv4 и порт;
   - сеанс;
   - поезд.
4. Узел помощника подключается **прямо к машинисту**. Он делает до 5
   попыток и переподключается при потере.
5. Он представляется пакетом `0x1700`:
   - id узла: хеш его имени;
   - сеанс.

   Машинист сопоставляет его по этим двум.
6. По этой связи:
   - машинист передаёт поезд: `0x4620`, с вагонами `0x4621`, локомотивом
     `0x4628`, электро / дизель `0x4629` / `0x462A`;
   - машинист передаёт кабину: `0x4624`..`0x462C`, `0x4631`;
   - помощник отправляет `0x4623` (PROBABLE: свои действия в кабине).

**Кто передаёт — CONFIRMED** (`0x424488`). Клиент передаёт, когда
выполнены два условия:
- его поезд вида PLAYER;
- узел существует.

Направление связи не важно. Клиент передаёт:
- `0x4620` каждые 500 мс;
- полное состояние кабины (`0x4624`…) каждые 60 с.

Отправкой занимается поток отправки (`0x5CEA84`).

**Какая сторона слушает — CONFIRMED.** Машинист всегда слушает
(`0x52D184` → `0x52CF80`); помощник всегда подключается сам (`0x52D074`).
Поэтому машинист должен принимать входящий TCP на этом порту: мешают NAT и
брандмауэры.

## NetworkNode (`rts1.exe` `0x52B6E4`) — CONFIRMED

**Поток:**
- поток с окном сообщений «RTS Network Node \<name\>»;
- семафоры `NNNodeSemaphore`, `NNInSemaphore`, `NNOutSemaphore`.

**Связи** в трёх состояниях:
- 1: принята, ещё не назвалась;
- 2: назвалась;
- 4: исходящая.

**Флаги** (+92):
- `0x10`: доставлять пакеты связей в состоянии 2;
- `0x20`: доставлять пакеты связей в состоянии 4;
- `0x40`: доставлять пакеты неназвавшихся связей;
- `0x800`: читать обычное обрамление от неназвавшихся связей;
- `0x1000`: доставлять события узла.

**Приветствие** (`0x52DAD8`): `u16 0x1700`, `u32 14`, `u32` id узла, `u32`
сеанс. Неизвестный собеседник допускается, только когда узел принимает
любого.

**События узла** доходят до обработчика как `0x1701`:
- 1: подключено;
- 2: соединение потеряно;
- 3: закрыто;
- 6: переподключено;
- 7: новая связь.

**Исходящие связи** повторяют попытку каждые 10 с до предела попыток («Max
connection attempts reached»). Пакеты можно пересылать из одного списка
связей в другой (`0x52CB8C`).

## Почему диспетчер не может подключиться к `rts1.exe` — CONFIRMED

1. **Порт.** У диспетчера по умолчанию 800, выделенный сервер. Мини-сервер
   сидит на первом свободном порту из 801..16000.
2. **Нет ответа.** На правильном порту `0x4500` доходит до `0x4CA588` как
   пакет от неназвавшейся связи. Ветки для него нет, поэтому ничего не
   возвращается: ни ответа, ни кода ошибки, соединение остаётся открытым.
   - Таймер подключения диспетчера ждёт ответа, который никогда не придёт.
     PROBABLE: тайм-аута у него нет.
3. **Не с чем говорить.** Даже допущенный, он не нашёл бы:
   - ни одного пакета диспетчера: ни `0x4504`..`0x450E`, ни обработки
     команд `0x4505` / `0x4506` / `0x4508` / `0x4509`;
   - прав диспетчера;
   - серверной логики пульта (маршруты, централизация, формы поездов).

## Канал данных между клиентами openRTS через сервер RTS — CONFIRMED (код), ещё не проверен

Два клиента openRTS на оригинальном `rts_server.exe` могут обмениваться
своими данными:
- Использовать пакет, который сервер пересылает непрочитанным аудитории 2:
  `0x461D` или `0x463F`, состояние объекта мира. До 15 360 байт предела
  сервера, по TCP.
- Начать нагрузку с 20 байт, не называющих ни одного объекта мира (u32 id,
  12 байт положения, u32), затем положить после них свои данные openRTS.

Как к этому относятся все остальные:
- **Оригинальные клиенты** ищут объект по этим 20 байтам в пределах 50 м
  (`0x4E0E4C`). Ничего не находят, дальше не читают и ничего не пишут в
  журнал.
- **У диспетчера** нет ветки для этих id, и он их пропускает.
- **Сервер** пересылает их всем в игре, кроме отправителя. Он их не
  читает.

**Ограничения:**
- Адресации нет: каждый получает каждый пакет, поэтому получатель и метка
  кладутся внутрь.
- Действуют ограничения пакетов сервера. Каждый пользователь считается в
  окнах по 5 с (`0x44563C`); при превышении предела сервер отвечает
  `0x4706` и выгоняет пользователя. Умолчания, которые можно изменить в
  настройках сервера:
  - 1 000 пакетов в секунду всего;
  - 500 в секунду для `0x4639` / `0x463A` / `0x463D`.
- Дороже всего стоит исходящий канал сервера: каждый пакет туннеля
  копируется каждому игроку в игре.
- Полная трассировка данных сервера записывает байты.
- `0x461B` тоже подошёл бы (отрицательные id вагонов и действие 1 ничего не
  делают), но это настоящее действие, и его лучше не трогать.
- Id аудитории 4 требуют настоящего поезда и доходят только до игроков
  рядом с ним.

## Для openRTS (шаг 6)

**Режим Legacy** означает разговор на этом протоколе:
- TCP и обрамление выше;
- входы `0x4600` / `0x4500` с версией 101, ответ и коды ошибок;
- стартовый снимок;
- положения поездов каждые 1,5 с с экстраполяцией на принимающей стороне;
- стрелки, сигналы и время решает сервер.

**Один сервер, обе роли.** Сервер openRTS может принимать игроков и
диспетчеров в одной программе, как `rts_server.exe`. Игра, которую держит
игрок, — тот же сервер, работающий внутри игры; тогда к нему может
подключиться и диспетчер.

**Помощники без открытого порта:**
- **Клиенты openRTS (Legacy выключен).** Прямой связи нет вовсе. Пакеты
  помощника и машиниста идут по их обычным соединениям с сервером, а
  сервер пересылает их по поезду. Цена — ещё один переход задержки и
  трафик сервера (`0x4620` дважды в секунду).
- **Помощник RTS.** Он всегда подключается сам. Сервер openRTS может дать
  ему свой адрес и порт ретранслятора в `0x461F` типа 1 и пересылать байты.
  Помощнику открытый порт никогда не был нужен.
- **Машинист RTS.** Он всегда слушает, но ему можно велеть подключиться
  самому: сервер отправляет ему `0x461F` типа 1 вместо типа 2, указывающий
  на ретранслятор. Ретранслятор сводит два исходящих соединения по сеансу
  их приветствий `0x1700` и соединяет их трубой. Передача и пакеты
  помощника не зависят от направления связи. CONFIRMED проверкой ниже.

**Проверка, 2026-11-03.**
- Обстановка:
  - один ПК: `rts_server.exe` на порту 800, два `rts1.exe` из двух папок,
    ВЛ80с на Кубани;
  - посредник перед сервером (`build/mp_test/mp_proxy.py`, не в
    репозитории).
- Результаты по режиму посредника:
  - **наблюдение:** помощник связывается прямо с машинистом на порту 801 и
    видит кабину;
  - **только помощник через ретранслятор:** работает;
  - **обе стороны подключаются сами, нигде нет открытого порта:**
    работает, переключатели кабины следуют в обе стороны.
- Найдено по пути, CONFIRMED, если не отмечено:
  - Сервер снова отправляет машинисту `0x461F` типа 2 с **новым сеансом**
    каждый раз, когда входит помощник (он отправляется и при собственном
    входе машиниста, если помощник был назначен заранее).

    Второй тип 1 машинисту заставляет его оборвать свои исходящие связи
    (`0x52D4F0`), и новая связь тоже не открылась. PROBABLE: обрыв
    обрабатывается после того, как сделана новая связь.

    Поэтому ретранслятор сообщает машинисту один раз и сопоставляет
    последующие сеансы того же помощника с первым. Он каждый раз отвечает
    серверу за машиниста:
    - `0x461F` подтип 4: id помощника, порт, сеанс, поезд;
    - раскладка байт в байт совпадает с ответом настоящего машиниста.
  - `0x461F` типа 1 от настоящего сервера — 190 байт. `rts1.exe` читает
    первые 54: имя, адрес, порт, сеанс, поезд, номер, 2 байта. Остальное —
    UNKNOWN.
  - По связи:
    - ВЛ80с: `0x4620` по 223 байта примерно каждые 0,5 с;
    - при подключении помощник отправляет `0x4623` (22 байта), запрос
      синхронизации;
    - машинист отвечает всей кабиной, `0x4624` (5 758 байт).
  - Машинист начинает передавать, как только его соединение поднято, ещё
    до появления помощника. Ретранслятору стоит это отбрасывать, а не
    ставить в очередь.

**Сцепка поездов двух игроков.**
- Legacy включён: как в RTS (выше), чтобы клиенты RTS видели то, чего ждут.
- Legacy выключен:
  - сцепку решает сервер за один шаг, так что два клиента не могут
    выполнить её оба;
  - игрок, чей поезд забрали, выбирает: остаться в общем поезде помощником
    или отцепиться и забрать свой локомотив.

**Следующие шаги разбора:**
- нагрузки пакетов диспетчера `0x45xx`;
- семейство `0x4620`;
- оставшиеся поля `0x4603`;
- снимок с полной трассировкой данных сервера, чтобы проверить числа и
  период;
- после сцепки: отбрасывает ли сервер `0x4603` от игрока, который поездом
  уже не владеет, и кому достаётся часть, отцепленная потом (`0x44FE34`).
