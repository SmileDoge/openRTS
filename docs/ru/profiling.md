# Профилирование с Tracy

openRTS можно собрать с клиентом [Tracy](https://github.com/wolfpld/tracy)
(BSD-3) — профилировщика кадров в духе VProf из Source, Profiler из Unity и
Unreal Insights: все размеченные зоны всех потоков на одной временной шкале,
кадр за кадром, со статистикой, графиками и кадрами, которые подтормозили.
Клиент — необязательная зависимость, по умолчанию выключен: без него зоны
компилируются в ничто, и код Tracy не собирается и не линкуется. В
выпущенных сборках его нет.

## Сборка

```powershell
cmake -S . -B build-tracy -DOPENRTS_ENABLE_WGPU=ON -DOPENRTS_WGPU_ROOT=C:\sdk\wgpu-native -DOPENRTS_ENABLE_TRACY=ON
cmake --build build-tracy --config Release
```

Отдельная папка сборки оставляет обычную как есть (опцию можно переключить и
в существующей сборке, тогда пересоберётся всё). Клиент, Tracy v0.14.1,
CMake скачивает сам.

Клиент работает по требованию: пока профилировщик не подключился, он ничего
не хранит, и слушает только localhost (порт 8086). Без подключения сборка с
Tracy работает так же быстро, как обычная (станция с девятью поездами: все
стадии в пределах шума между прогонами).

## Профилировщик

Версия профилировщика должна совпадать с версией клиента: Tracy 0.14.1,
`windows-0.14.1.zip` со
[страницы релиза](https://github.com/wolfpld/tracy/releases/tag/v0.14.1).

- `tracy-profiler.exe` — окно. Запустить игру, затем подключиться к
  `127.0.0.1` (она есть и в списке найденных клиентов). Statistics (сумма,
  среднее и максимум по зонам), Find zone (времена одной зоны гистограммой),
  график кадров сверху (каждый столбик — кадр: щелчок по медленному
  показывает его на шкале).
- `tracy-capture.exe -o run.tracy -s 30` — записывает 30 с без окна (ждёт
  запуска игры), чтобы открыть профилировщиком потом.
- `tracy-csvexport.exe run.tracy` — статистика зон в CSV; `-u` перечисляет
  каждую зону с началом, длительностью и потоком.

С подключённым профилировщиком кадр немного медленнее (несколько десятых
миллисекунды на станции): сравнивать стоит, куда уходит время, а не сотые.

## Что размечено

| Зона | Где |
|---|---|
| `update`, `panel`, `wait`, `begin`, `backgr`, `cull`, `prepare`, `effects`, `models`, `foregr`, `end`, `post`, `encode`, `join`, `submit` | стадии кадра, как в списке стадий панели; `FPS limit` между кадрами |
| `scene: update`, `scene: submit` | сцена маршрута каждый кадр |
| `trains: update`, `trains: physics step`, `trains: DLL host step`, `trains: sound`, `trains: submit` | поезда: обновление, шаг симуляции, шаг DLL локомотивов в 32-битном хосте (вместе с ожиданием его), звуки, модели для рендера |
| `trains: DLL world feed`; `DLL: request`, `DLL: write the request`, `DLL: waiting for the host`, `DLL: read the reply` | части шага DLL: мир для DLL, запрос (собран и записан в общую память), ожидание 32-битного хоста (его работа и два переключения потоков), ответ |
| `signals`, `network`, `audio`, `route streaming` | обновление этих подсистем |
| `models: prepare` с `models: primitives`, `models: batches`, `models: waiting for the depth draws`, `models: instances`, `models: uploads`; `models: depth draws` | группировка вызовов и загрузки рендера; группировка для проходов глубины идёт в потоке |
| `models: main pass`, `models: depth pass`, `terrain: main pass`, `terrain: depth pass` | запись проходов |
| `effects: pass` (текст говорит, какой: `sun cascade 1`..`4`, `cab focus`, `lamp shadow`, `camera depth, GTAO, clusters`), `effects: begin frame`, `effects: focus and lamps` | новый рендер: его проходы в потоках (в каждом `effects: record` и `effects: finish` — `wgpuCommandEncoderFinish` у wgpu) и подготовка кадра |

Потоки называются `worker 1`, `worker 2`... Графики: `draw calls`,
`draw commands`, `model instances`. Кадр заканчивается после `submit`.

Зона каждой стадии кадра открывается под именем стадии, которая шла
следующей в прошлом кадре (Tracy группирует статистику по имени, с которым
зона открылась), и переименовывается на шкале, если закончилась другой:
так бывает только в первом кадре.

## Как добавить зону

```cpp
#include <openrts/core/profile.hpp>

void TrainView::step_trains() {
    OPENRTS_ZONE("trains: physics step");
    ...
}
```

`OPENRTS_ZONE("область: что")` размечает до конца области видимости;
`OPENRTS_ZONE_TEXT(text, size)` добавляет к зоне подробность (какой проход,
какой поезд); остальное — `OPENRTS_THREAD_NAME`, `OPENRTS_PLOT`,
`OPENRTS_FRAME` (`include/openrts/core/profile.hpp`). Имена — строковые
литералы. Они доступны в каждой библиотеке, которая линкует `openrts_core`.
Зона стоит около 20 нс при подключённом профилировщике: на кадр, на проход,
на поезд — можно; на экземпляр, на треугольник — нет.

## Первый взгляд (2026-11-07)

Станция из заметок про multi-draw (девять поездов, новый рендер, 30 FPS),
последние 8 с прогона, мс за кадр в потоке отрисовки:

| Зона | мс |
|---|---|
| `update` | 2,98 |
| из них `trains: DLL host step` | 1,52 (2,3 мс каждый шаг, два кадра из трёх) |
| `prepare` | 1,82 |
| из них `models: batches` | 1,23 |
| `encode` | 1,36 |
| `cull` | 1,13 |
| из них `trains: submit` | 0,65 |
| `models` | 0,42 |

В потоках: проходы всего 3,7 мс за кадр, `models: depth draws` 1,3. Шаг DLL
локомотивов ждёт 32-битный хост в потоке отрисовки: это самая крупная
отдельная часть кадра, которую раньше не было видно (её прятала стадия
`update`).

**`encode` никого не ждёт.** wgpu проверяет и переводит команды прохода в
`wgpuCommandEncoderFinish`, а не при записи. С выключенной многопоточной
записью (все проходы в главном буфере команд) `encode` — 3,1 мс: 1,2 у
основного прохода и около 1,9 у проходов теней и камеры. С включённой
`effects: finish` в потоках (2,1 мс за кадр, из них 1,5 — пока идёт
`encode`) и `encode` (1,28) в сумме дают то же с точностью до 0,2 мс: друг
друга они почти не тормозят. `finish` стоит в 1,4 раза больше записи у
проходов глубины и в 3,3 раза у основного прохода (много смен групп
ресурсов): короче `encode` станет только с меньшим числом команд. Проходы
камеры, самые длинные (запись 0,73 мс, `finish` 1,08), с тех пор ставятся в
очередь первыми: потоки заканчивают на 0,3 мс раньше `encode` (медиана),
`join` 0,10 -> 0,02 мс.

**Группировка в плоских массивах** (2026-11-08). `models: batches` каждый
кадр строила около 1800 групп, у каждой свой вектор, в `unordered_map`, и
так же группировались вызовы глубины в потоке. Теперь обе берут плоские
массивы, которые живут между кадрами: таблицу групп (открытая адресация,
очищается новым поколением), номер группы у каждого элемента, экземпляры
групп раскладываются подсчётом; кадр, в котором групп не больше, чем
раньше, ничего не выделяет. Порядок тот же: группы по pipeline и модели,
иначе как пришли; экземпляры в порядке элементов; смешиваемые примитивы в
своём порядке (проверка, гонявшая старый код рядом с новым, не нашла
разницы за 600 кадров). По две трассы, последние 8 с:

| мс за кадр | до | после |
|---|---|---|
| вся работа CPU (без `wait`) | 7,53, 7,81 | 6,76, 6,37 |
| `prepare` | 1,59, 1,62 | 0,77, 0,64 |
| `models: batches` | 1,19 | 0,36, 0,35 |
| `models: depth draws` (поток) | 1,32 | 0,19, 0,19 |

Кадры те же (`--paused`, снимок на 45-й секунде, когда станция
догрузилась): Vulkan и OpenGL на пути RTS — байт в байт, новый рендер на
Vulkan и DirectX 12 и путь RTS на DirectX 12 — в пределах 2 пикселей (как
два прогона одной сборки).

**Шаг DLL** (2026-11-08). 20 шагов в секунду, по одному на шаг физики
(`train_step` 0,05 с): 1,5 мс за кадр выше — это 2,1 мс на шаг при 30 FPS
(в двух кадрах из трёх по шагу); при 145 FPS это в среднем 0,3 мс за кадр,
2,1 мс в каждом седьмом кадре. Из 2,1 мс шага (ЭД9М, 8 вагонов) на нашей
стороне 0,05 (запрос, мир, ответ), остальное — ожидание хоста. Внутри хоста
(замерено там для проверки, замеры не оставлены): 1,4 мс на обработку
шага, из них 1,3 — `Run` вагонов; из этого `ED9M.dll` — 0,03 мс на 8
вызовов, `Usavp.dll` и `RTSConnector.dll` — 0,07, `Brakes.dll` — 1,2, а из
времени `Brakes.dll` 1,2 мс уходит в наш `RTSGetObjectByName`: 676 вызовов
за шаг (параметры ищутся по имени на каждом `Run`), каждый — линейный
перебор с `lstrcmpiW`, около 1,8 мкс на вызов. Остальные 0,7 мс ожидания —
пробуждение хоста и переключение потоков на ответе.

**Ответы поиска по имени запоминаются** (2026-11-08, docs/train-dll.md
«Как сделано»). Хост хранит объект, найденный по имени; DLL и обмен с
хостом не менялись. Со сверкой `OPENRTS_DLLHOST_NAME_CHECK` на ЭД9М на
станции 853 759 запомненных ответов перепроверены перебором, расхождений
нет; 309 записей, 91 имя спрашивали несколько владельцев (до 8, по
вагону), у каждого вагона свой объект. Поиск: 0,78 мс в первом шаге после
очистки (317 промахов, 564 попадания), дальше 0,06 мс за шаг (около 712
попаданий, промахов нет). По две трассы, последние 30 с (900 кадров, 30
FPS):

| мс | до | после |
|---|---|---|
| шаг DLL, среднее | 2,14, 2,18 | 1,01, 0,97 |
| шаг DLL, P95 / P99 | 2,52–2,60 / 2,64–2,84 | 1,24–1,27 / 1,58–1,64 |
| работа CPU за кадр, среднее | 6,38, 6,38 | 5,52, 5,45 |
| работа CPU за кадр, P95 / P99 | 8,1–8,2 / 9,1–11,2 | 6,69 / 8,1–8,4 |
| кадры с шагом / без шага | 7,20 / 4,72 | 5,92 / 4,62 |
| кадр (ограничение 30 FPS), P95 / P99 | 36,3–36,5 / 37,2–39,0 | 35,0–35,2 / 35,7–36,2 |

Работа CPU — кадр без `wait` и без ожидания ограничителя FPS (с
ограничением сам кадр — 33,3 мс). Одиночные кадры по 27–42 мс (загрузка)
есть и до, и после. Что осталось от шага: собственные 0,25 мс хоста и
0,7 мс на его пробуждение и переключение обратно.
