# AGENTS.md

## 0. Главный режим работы

Этот файл описывает, как работать над `openRTS`.

Главное правило: **если пользователь просит что-то сделать в проекте, делай это сейчас и доводи до рабочего результата.**

Не превращай обычную implementation-задачу в консультацию, архитектурное эссе или обещание будущей работы.

### 0.1. Короткие команды пользователя уже являются достаточным разрешением на работу

В контексте проекта такие фразы, как:

```text
сделай X
делай
продолжай
давай X
надо бы X поправить
поправь X
добавь X
вынеси X
сделай нормально
сделай как в OpenRails
теперь надо X
```

означают: **внеси соответствующие изменения в `openRTS/`, проверь их и верни уже сделанный результат.**

Не требуй от пользователя превращать каждую просьбу в формальное техническое задание с acceptance criteria.

Если формулировка короткая, используй текущий контекст, состояние репозитория и здравый инженерный смысл, чтобы определить ожидаемый результат.

Если пользователь говорит просто `делай` или `продолжай`, продолжай текущую незавершённую задачу до её естественного завершения. Не пересказывай план заново.

### 0.2. Implementation-задача означает execution, а не planning

Если пользователь явно не просит только анализ, обсуждение или план, рабочий цикл должен выглядеть так:

```text
inspect relevant code
-> decide locally
-> edit
-> build/test
-> inspect failure
-> edit
-> build/test
-> repeat
-> final report
```

Планирование допустимо как внутренняя часть работы, но **не является результатом**.

Нельзя заканчивать implementation-ход сообщениями вида:

```text
"начну с ..."
"следующим шагом ..."
"сначала вынесу ..."
"после этого подключу ..."
"дальше нужно ..."
"архитектура понятна, теперь можно реализовать ..."
"это большой рефакторинг, поэтому сделаю его отдельным milestone"
```

Если собираешься написать такую фразу, выполни описанную работу вместо этого.

**Future tense is not a substitute for tool execution.**

### 0.3. Пользовательский результат определяет milestone

Если пользователь попросил:

```text
сделай систему материалов
вынеси рендеринг моделей из viewer
добавь прозрачность
переделай lifetime GPU-моделей
```

то именно этот результат является текущим milestone.

Не уменьшай, не откладывай и не разбивай его на несколько пользовательских ходов только потому, что задача:

- большая;
- затрагивает несколько файлов;
- архитектурная;
- содержит ownership/lifetime;
- требует нового класса или API;
- требует нескольких циклов build/fix/test.

Внутренне разбивать работу на подзадачи можно и нужно. Но это **внутреннее разбиение**, а не повод вернуть управление после первых 10%.

Неверные точки остановки:

- только объявлены `struct`/`enum`/interface;
- создан пустой новый файл;
- перенесена только половина подсистемы;
- добавлен временный `if`, но сама запрошенная система не появилась;
- код компилируется, но новая функциональность ещё не подключена;
- сделан первый успешный build, но acceptance behavior ещё не проверен;
- проведено исследование reference implementation, но код проекта не изменён.

### 0.4. Не спрашивай разрешение на обычные локальные инженерные решения

Самостоятельно принимай обратимые решения внутри текущего scope, например:

- имя локального/private типа;
- расположение helper-функции;
- разбиение `.cpp`/`.hpp`;
- выбор очевидной RAII-обёртки;
- способ кэширования внутри renderer;
- необходимость небольшого enum;
- порядок приватных методов;
- простая адаптация существующего API;
- добавление релевантного unit/smoke test.

Сначала посмотри существующий стиль проекта и выбери наиболее простой совместимый вариант.

Не перекладывай такие решения на пользователя.

### 0.5. Когда действительно нужно остановиться

Останавливайся и проси решение пользователя только если есть **реальный блокер**, например:

- два взаимоисключающих варианта с существенными долгосрочными последствиями для публичной архитектуры/ABI/формата;
- требуется разрушительное или трудно обратимое действие;
- требуется изменение защищённой оригинальной директории `RTS/`;
- нужны недоступные credentials/license/secret/external resource;
- необходимый файл или исходный материал реально отсутствует;
- доступные инструменты объективно не позволяют продолжить;
- пользователь должен выбрать продуктовую семантику, которую нельзя надёжно вывести из проекта/RTS/OpenRails/runtime.

Большой объём работы, ошибки компиляции, отсутствие Git, отсутствие необязательной утилиты или необходимость читать несколько файлов **не являются блокерами**.

### 0.6. Ошибки исправляй сам

Обычные ошибки:

- compile;
- link;
- test;
- parser/runtime;
- bad include;
- wrong CMake target;
- API mismatch;
- очевидная regressия после собственного изменения;

исправляй самостоятельно и повторяй проверку в том же рабочем ходе.

Не возвращай ошибку пользователю как результат, если можешь разумно её исправить.

### 0.7. Критерий готовности по умолчанию

Если пользователь не задал другое, implementation-задача готова, когда:

1. запрошенное поведение реально реализовано и подключено;
2. затронутые targets собираются;
3. релевантные тесты проходят;
4. для viewer/tool выполнен разумный smoke-test;
5. если задача касается реальных RTS/MSTS assets, по возможности проверен реальный подходящий asset;
6. собственные изменения не оставили очевидную временную заглушку вместо запрошенной архитектуры.

Если полноценную интерактивную проверку нельзя автоматизировать, выполни максимально близкую проверку и честно укажи ограничение в финальном отчёте.

### 0.8. Финальный ответ после implementation

После завершения кратко сообщи:

- что изменено;
- какие ключевые архитектурные решения приняты;
- чем проверено;
- есть ли конкретные оставшиеся ограничения, которые действительно относятся к задаче.

Не заканчивай финальный ответ списком обещаний того, что ещё собираешься сделать вместо уже выполненной задачи.

## 1. Не путай implementation и research/reverse

В проекте есть два разных режима работы.

### IMPLEMENTATION MODE

Используется для запросов `сделай`, `добавь`, `исправь`, `рефактори`, `вынеси`, `подключи`, `реализуй` и подобных.

Приоритет:

```text
working code
-> correct architecture inside requested scope
-> build/tests/runtime verification
-> concise report
```

Нужное исследование выполняй точечно и сразу возвращайся к реализации.

### RESEARCH / REVERSE MODE

Используется, когда пользователь просит выяснить поведение RTS, восстановить ABI/формат/структуру, проанализировать IDA или сравнить источники.

Приоритет:

```text
evidence
-> confidence
-> cross-check
-> documented finding
```

Здесь нельзя превращать догадку в факт.

**Правила осторожного reverse-engineering не должны парализовать обычную разработку нового кода.**

## 2. Проект

`openRTS` — независимая реализация RTrainSim (RTS) с совместимостью с существующим RTS/MSTS-контентом и постепенным восстановлением поведения старого движка на современной архитектуре.

Основные задачи проекта:

- читать оригинальные RTS/MSTS assets;
- восстанавливать необходимые форматы и runtime semantics;
- реализовывать собственные современные подсистемы;
- сохранять совместимость там, где она является observable behavior/content contract;
- не копировать старую внутреннюю архитектуру без необходимости.

Текущий репозиторий и существующий код являются источником истины о фактическом состоянии реализации. Не полагайся на этот файл как на список уже завершённых features: перед изменением быстро осмотри соответствующие файлы.

### Архитектурное направление renderer

Текущая разработка viewer/renderer использует WebGPU.

Не привязывай `formats`, `assets`, simulation/domain и compatibility layers к WebGPU сильнее, чем необходимо. Renderer backend должен оставаться локализованным в renderer/platform слое.

Не переносить старую OpenGL state-machine архитектуру RTS буквально.

## 3. Рабочие каталоги и безопасность

Основные каталоги:

- `openRTS/` — рабочая директория проекта. Здесь можно создавать и изменять код, документацию, tests, tools и build-файлы.
- `RTS/` — установленная оригинальная игра RTrainSim и материалы для анализа. По умолчанию **read-only**.
- `RTrainSimPlugins-premake/` — предыдущий reverse/plugin project. Используй как вторичный reference, по умолчанию **read-only**.
- `OpenRails/`, если присутствует, — reference implementation для MSTS semantics, по умолчанию **read-only**.

### Оригинальную RTS не изменять без явного запроса

Нельзя самостоятельно:

- изменять/перезаписывать `rts1.exe`;
- изменять оригинальные DLL;
- удалять, переименовывать или переносить игровые ресурсы;
- запускать build output в `RTS/`;
- конвертировать оригинальные assets in-place;
- "чистить" установленную игру.

Читать файлы RTS для анализа и тестов разрешено.

Если тест требует модификации ресурса, копируй его в каталог внутри `openRTS`, например:

```text
openRTS/testdata/
openRTS/scratch/
```

### IDA databases

Файлы `.i64`, `.id0`, `.id1`, `.id2`, `.nam`, `.til` являются отдельными артефактами reverse-engineering.

Их можно изменять только средствами IDA/IDA MCP и только если текущая reverse-задача это допускает.

Обычный код/build scripts не должны писать в IDA database.

## 4. Работа с пользовательскими формулировками

### "Сделай X"

Считай это запросом на реализацию X, включая необходимые локальные refactors, build и test.

### "Делай" / "Продолжай"

Продолжай текущую задачу. Не проси повторить ТЗ и не возвращай новый план.

### "Надо бы X поправить"

Если контекст явно относится к текущему проекту и изменение безопасно/обратимо, трактуй как просьбу исправить X.

### "Сделай как в OpenRails"

Обычно означает:

```text
найди релевантную семантику в OpenRails
-> пойми поведение/формат
-> сопоставь с RTS/MSTS data
-> реализуй независимо в openRTS
-> проверь
```

Это **не** означает механически копировать классы, код или архитектуру OpenRails.

### "Посмотри", "что думаешь", "как лучше"

Это анализ/обсуждение, если пользователь явно не добавил просьбу внести изменения.

## 5. Open Rails и лицензирование

Open Rails можно использовать как технический reference по MSTS:

- `.s`, `.sd`, `.eng`, `.wag`, `.con`, `.act` и другим форматам;
- material/shader/primitive semantics;
- routes/world/track structures;
- signal logic;
- MSTS naming and edge cases.

При использовании Open Rails:

- извлекай факты о формате, данных и наблюдаемом поведении;
- сверяй с реальными assets/RTS docs, когда это важно;
- пиши собственную реализацию в архитектуре `openRTS`;
- не делай построчный/механический порт GPL-кода;
- не копируй большие блоки исходного кода или комментариев.

GPL-лицензия Open Rails **не является причиной останавливаться**, если задача состоит в исследовании semantics и независимой реализации.

Если для конкретного поведения достаточно посмотреть 1-3 релевантных места, не исследуй весь Open Rails.

## 6. Источники для совместимости RTS/MSTS

Когда действительно нужен research, используй такой приоритет.

### 6.1. Официальные/project RTS материалы

Ожидаются в:

```text
docs/RTS/
    RTSFileFormat.dat
    RTSFileReference.html
    export.pdf
    ext.pdf
```

Также оригинальный `ts.h` может находиться примерно здесь:

```text
TRAINS/TRAINSET/tsrLoco_VL80k-125/CAB/ts.h
```

Если оригинальный `ts.h` доступен, используй его вместо реконструкции ABI "по памяти".

### 6.2. MSTS/Open Rails

Используй для MSTS format/semantic reference.

### 6.3. Предыдущий reverse project

`RTrainSimPlugins-premake/` содержит полезные ранее найденные детали, но это вторичный источник.

Там могут быть:

- experimental assumptions;
- hardcoded offsets;
- version-specific behavior;
- workaround'ы;
- неполный reverse.

Не переносить такие предположения в новый compatibility contract без проверки, если от них зависит ABI/формат/observable behavior.

### 6.4. IDA / IDA MCP

Используй для недокументированного RTS-specific runtime behavior и проверки конкретных неизвестных деталей.

### 6.5. Runtime verification

Если источники реально расходятся, сделай минимальную runtime-проверку вместо выбора по догадке.

## 7. Уверенность в reverse findings

Это правило относится прежде всего к reverse/research, а не к обычным приватным решениям нового кода.

Используй:

```text
CONFIRMED
PROBABLE
UNKNOWN
```

`CONFIRMED`:

- прямая документация;
- `ts.h`/символ;
- убедительные независимые xref/use sites;
- runtime test.

`PROBABLE`:

- сильная гипотеза с хорошим evidence, но остаётся разумная альтернатива.

`UNKNOWN`:

- слабое или недостаточное evidence.

Не выдавай guessed IDA field/function name за оригинальное имя автора.

Для важной восстановленной структуры полезно фиксировать:

```text
offset
size
type
candidate name
confidence
evidence
```

## 8. Принципы проектирования нового кода

### 8.1. Семантика важнее старой реализации

Сохраняй там, где нужно для совместимости:

- file format semantics;
- observable runtime behavior;
- physics/timing semantics;
- content expectations;
- ABI, если поддержка ABI явно является целью.

Необязательно сохранять:

- старую OpenGL state machine;
- внутренние addresses/offsets exe;
- старые global variables;
- старый threading model;
- исторические ограничения API, которые не видны контенту/пользователю.

### 8.2. Границы модулей

Ориентируйся на разделение:

```text
formats     CPU parsing / file semantics
assets      asset lookup/loading/resolution
renderer    GPU representation/rendering/materials
platform    window/input/backend platform details
simulation  domain state and simulation
compat      compatibility/legacy bridges
viewer      thin interactive/debug application
tools       standalone inspection/conversion/debug tools
```

Не протаскивай WebGPU-типы в `formats` только ради удобства renderer.

### 8.3. Viewer должен оставаться тонким

Viewer допустимо использовать для integration/smoke tests, но reusable renderer logic не должна навсегда жить в `viewer/main.cpp` или одном giant viewer source.

Когда renderer subsystem уже сформировалась, предпочитай:

```text
CPU asset/model
    -> GPU/renderable representation
    -> renderer draws it
```

Viewer отвечает прежде всего за:

- CLI;
- window/input loop;
- выбор/загрузку тестового asset;
- camera/user interaction;
- вызов renderer API.

### 8.4. GPU lifetime и ownership

Для GPU-resources предпочитай явный ownership/lifetime:

- upload/create один раз при загрузке/изменении, не каждый frame без причины;
- reusable `RenderModel`/эквивалент владеет per-model GPU resources;
- renderer владеет/кэширует общие pipelines/material/sampler state там, где это логично;
- освобождение ресурсов идёт через нормальный lifetime/RAII/move-only ownership либо другой ясный механизм;
- viewer не должен вручную знать внутренности каждого GPU buffer/bind group.

Не создавай абстракцию только ради красивого имени. Создавай её, когда она выражает реальную ownership/lifetime/API boundary.

### 8.5. Material system

Если работа касается материалов, не своди задачу к одному `bool transparent`, если данные/семантика требуют большего.

Обычно полезно разделять:

- material semantics;
- texture reference/addressing;
- alpha test/cutout;
- blend mode/pass;
- depth test/write policy;
- render ordering/sorting для transparent draw ranges;
- backend pipeline state/cache.

Конкретные режимы определяй по реальным RTS/MSTS/OpenRails semantics и текущему scope.

## 9. Scope: не giant rewrite, но и не micro-patch вместо задачи

Не расширяй запрос пользователя в несвязанный engine-wide rewrite.

Например, просьба исправить material system не является поводом одновременно переписать ECS, build system и весь asset pipeline.

Но правило "не делай giant rewrite" **никогда не должно использоваться для урезания явно запрошенного рефакторинга**.

Если пользователь попросил существенный refactor одного subsystem, этот refactor и есть разрешённый scope.

`Keep changes focused` означает:

- не переписывать несвязанные системы;
- не добавлять спекулятивные features;
- не менять public contracts без необходимости;
- не заниматься cleanup ради cleanup.

Это НЕ означает:

- сделать только первый файл;
- остановиться после объявления типов;
- отложить wiring/integration;
- заменить архитектуру временной заглушкой;
- попросить пользователя подтвердить каждый локальный шаг.

## 10. Исследование должно быть точечным

Если текущая implementation-задача упирается в конкретный неизвестный факт:

```text
какой sampler addressing ожидает MSTS material?
что означает конкретный prim_state?
какой callback вызывается первым?
```

исследуй именно этот вопрос.

После достаточного evidence немедленно возвращайся к реализации.

Не превращай маленький неизвестный флаг в reverse всей игры.

Если уже существующая документация/reverse notes содержат нужный ответ, используй их. Не повторяй исследование только ради ритуала.

## 11. Тестирование

### 11.1. После изменения кода

По возможности:

1. собери затронутый target/configuration;
2. запусти релевантные tests;
3. если есть viewer/tool, запусти smoke-test;
4. если изменение связано с parser/renderer asset semantics, проверь подходящий реальный RTS/MSTS asset.

Если build/test упал из-за собственного изменения, исправь и повтори.

### 11.2. Реальные assets

Оригинальные файлы можно читать напрямую, если тест read-only.

Если требуется изменить/конвертировать asset, сначала работай с копией внутри `openRTS`.

Не коммить большие чужие assets без явной необходимости/разрешения.

### 11.3. Parser tests

Для развивающихся parser'ов полезны tests на:

- valid input;
- optional/repeated nodes;
- unknown nodes;
- malformed data;
- invalid indices/counts;
- Unicode/legacy encoding, когда применимо;
- реальные edge cases, найденные на RTS/MSTS assets.

Не пытайся написать полный test matrix до реализации самой requested feature.

```text
git diff
```

но это вспомогательная проверка, а не prerequisite для разработки.

Если Git отсутствует:

- не останавливай задачу;
- не запускай `git init` без запроса;
- просто работай с файлами и в конце перечисли изменения.

Не выполнять автоматически:

```text
git reset --hard
git clean -fdx
```

Не удаляй незнакомые пользовательские изменения только потому, что они мешают красивому diff.

Не создавай commit автоматически, если пользователь явно этого не просил.

---

## 13. Вспомогательный tool failure не равен blocker

Если не работает необязательный инструмент, сначала ищи безопасный обходной путь.

Примеры:

- нет Git -> продолжить без diff;
- нет `pdftotext` -> использовать доступное чтение PDF;
- GUI IDA занята -> использовать существующую read-only DB/headless path, если задача это позволяет;
- нет Ninja -> использовать уже настроенный Visual Studio/CMake generator;
- один smoke-test CLI недоступен -> выполнить максимально близкий test path.

Не меняй architecture и не устанавливай случайные зависимости только ради обхода вспомогательной проблемы, если есть более простой путь.

## 14. Документация reverse findings

Значимые подтверждённые findings лучше сохранять в `docs/reverse/`, например:

```text
docs/reverse/renderer.md
docs/reverse/formats.md
docs/reverse/dll-abi.md
docs/reverse/structures.md
docs/reverse/functions.md
```

Это особенно важно для:

- ABI;
- offsets/layouts;
- undocumented RTS behavior;
- callback lifecycle;
- parser/runtime linkage;
- material/renderer semantics, выясненных через IDA.

Но **не превращай запись документации в prerequisite каждой маленькой code change**.

Если пользователь просил implementation, сначала должен появиться рабочий implementation. Документируй найденный reverse-факт тогда, когда это полезно для будущей совместимости.

Пример reverse note:

```markdown
## Function 0x0045ABCD - LoadSomething

Confidence: PROBABLE

Evidence:
- caller A passes parsed Shape node;
- caller B stores result into SceneObject+0x68;
- function opens `.s` files;

Open questions:
- ownership of texture list;
- meaning of flags at +0x24.
```

## 15. IDA / IDA MCP

Используй IDA как точечный инструмент для неизвестных RTS-specific details.

Хорошие задачи:

```text
Find callers/callees of X.
Trace where object Y is allocated.
Find accesses to structure offset Z.
Find parser for token "LibraryModule".
Trace GetProcAddress for locomotive DLL exports.
Identify field populated by a parser node.
Compare fixed-function and shader rendering paths.
```

Плохие задачи без дополнительного scope:

```text
Reverse the whole game.
Rename everything.
Convert the executable to C++.
```

Перед массовыми изменениями IDB собирай evidence.

Не переименовывай сотни функций по слабым гипотезам.

## 16. Уже известные RTS-specific факты

Этот раздел даёт стартовые знания. Для критического ABI/format contract при необходимости перепроверяй первичный источник.

### 16.1. Связь с MSTS

RTS совместим с существенной частью MSTS-контента и расширяет его собственными возможностями.

Важны как минимум:

- Shape/Shape Description;
- Engine/Wagon;
- Activity/Consist;
- RTS-specific model/environment extensions;
- cab/salon/animation/light/effects extensions.

### 16.2. `RTSFileFormat.dat`

Рассматривай его как потенциальный машиночитаемый источник схемы RTS formats.

Если generic schema/AST действительно упрощает несколько форматов, это полезно. Но не строй огромный генератор типов только потому, что такая возможность существует.

### 16.3. DLL API локомотивов

Существующие RTS locomotive DLL являются Win32/32-bit.

Документация/`ts.h` описывают, среди прочего:

```text
Init
ChangeLoco
LostMaster
CanWorkWith
CanSwitch
Switched
Run
ALSN
SpeedLimit
```

И interface objects вроде:

```text
Locomotive
ElectricLocomotive
DieselLocomotive
Engine
ElectricEngine
DieselEngine
Cabin
SignalsInfo
SpeedLimitDescr
TrackItemsItem
AuxLibrary
```

Если основной `openRTS` остаётся x64, старую x86 DLL нельзя загрузить прямо в тот же процесс.

Не принимай крупное новое решение о legacy DLL architecture молча, если текущая задача прямо требует изменить этот contract. Отдельный x86 host/IPC является допустимым направлением, но фактическое состояние репозитория всегда проверяй перед изменением.

### 16.4. Renderer findings из RTS

Оригинальный RTS использует OpenGL, включая shader и legacy fixed-function paths.

Сильный рабочий candidate layout вершины из reverse:

```cpp
struct Vertex
{
    float position[3];    // +0x00
    float normal[3];      // +0x0C
    float uv0[2];         // +0x18

    // +0x20..+0x27: UNKNOWN

    uint8_t attrib3[4];   // +0x28
    uint8_t attrib4[4];   // +0x2C
}; // stride 0x30 / 48
```

Наблюдалось:

```text
position : 3xf32 @ +0
normal   : 3xf32 @ +12
uv       : 2xf32 @ +24
attrib3  : 4xu8  @ +40
attrib4  : 4xu8  @ +44
stride   : 48
```

Не придумывай назначение `+0x20..+0x27` без дополнительного evidence.

Indices:

```text
primitive topology: triangles
index type: uint32
index_count = triangle_count * 3
```

Старый GPU upload/ownership нужен как evidence поведения, но его lazy OpenGL resource model не обязан копироваться в новый renderer.

## 17. Имена и код-стиль

В новом коде используй нормальные domain names.

Не протаскивай IDA-имена вроде:

```text
sub_4ABCDE
v72
dword_...
```

в production/domain API.

Для неизвестной восстановленной сущности допустимы `Candidate*`, `Unknown*` или явный комментарий hypothesis до подтверждения.

Следуй существующему style проекта. Не выполняй массовый style-only rewrite вместе с функциональной задачей без необходимости.

## 18. Что считать хорошей работой агента

Хорошая implementation-сессия выглядит примерно так:

```text
user: "сделай систему материалов и прозрачность, посмотри OpenRails"

agent:
- читает текущий parser/renderer;
- точечно находит material semantics в OpenRails;
- проектирует локальный Material model;
- протягивает prim_state/material data;
- реализует opaque/masked/blended behavior;
- настраивает depth/blend/sampler state;
- собирает;
- исправляет ошибки;
- тестирует реальный shape;
- возвращает краткий отчёт о готовом результате.
```

Плохая сессия:

```text
- читает файлы;
- пишет план;
- объявляет один enum;
- говорит "следующим шагом подключу renderer";
- возвращает управление.
```

Ещё один хороший пример:

```text
user: "теперь нормально вынеси отрисовку моделей из shape_viewer и сделай lifetime"

agent:
- определяет существующие ownership boundaries;
- создаёт полноценный renderer-side model representation;
- переносит GPU resource lifetime;
- подключает viewer к новому API;
- удаляет старое дублирование;
- собирает и проверяет реальный asset;
- только после этого отвечает.
```

Не называй крупную, но ясно поставленную задачу "слишком большой" просто для того, чтобы сделать лишь первую часть.

---

## 19. Главный принцип

Для нового кода:

> **Понимай задачу, принимай локальные решения, реализуй, проверяй и доводи до рабочего состояния.**

Для reverse-engineering:

> **Документируй то, что известно; проверяй то, что можно измерить; не превращай догадки в спецификацию.**

Оба принципа важны, но осторожность reverse-engineering не должна превращать разработку `openRTS` в бесконечное планирование.
